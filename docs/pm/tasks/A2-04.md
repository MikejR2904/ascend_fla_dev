# A2-04 在模拟器里定位 `c1-multihead-o-corrupt` 的确切根因（只诊断，不修）

- 波次 / SoC：W0 / any。纯主机侧，跑 sim / pipesim，a5 与 a2 profile 各跑一遍
- 优先级：P0 · 时限：12h · 依赖：无
- 需要：ascriptor workspace
- 写集：`benchmarks/diag_c1_multihead.py`
- 证据目录：`tmp/A2-04/`

## 为什么现在做

这是仓里唯一的 P0，而且是静默错误：输出有限、量级正常、`final_state` 正确，只有逐元素内容是错的。
A2 的 KDA 单元（A2-03）从同一份 kernel 源码派生，会把这个缺陷一起带过去。按 `AGENTS.md` §6.5，
动手修之前必须先定位到确切原因，而目前只掌握症状规律。

## 背景（摘录）

上游 kernel 是 ascriptor `kernels/projects/a5/kda_fwd/kernels/recurrent.py` 里的 `kda_sub45_fused_kernel`。

症状在 Ascend950PR 上实测过，记在 `docs/plan.md` 的"真实形状精度验收"：C=1（T=64）且一个 cube 核要连续处理
多个头时，`o` 内容错，而正确的恰好是每个核分到的最后一个头。

| block_dim | HV=2 | HV=4 | HV=8 | HV=16 |
|---|---|---|---|---|
| 1 | 仅头 1 对 | 仅头 3 | 仅头 7 | 仅头 15 |
| 2 | 全对 | 头 1,3 | 头 3,7 | 头 7,15 |
| 4 | 全对 | 全对 | 头 1,3,5,7 | 头 3,7,11,15 |

`pair_begin/pair_end` 按 `GetCubeIdx()/GetCubeNum()` 切 `B*HV`，而 `GetCubeNum() == block_dim`，
所以安全条件是 `B*HV ≤ block_dim`。C≥2 全对，因为 chunk 循环跑第二遍时补上了缺的那次同步。

kernel 源码里有句注释：`auto sync is not used here because the nested for loops interfere with it`。
同步是手写的，而手写那份假设了 C≥2。

缺口记在 `gaps.json` 的 `c1-multihead-o-corrupt`，怀疑 pair 循环跨头时缺一次 L0C / L1 的同步，
"还没定位到确切缺哪一次 DEvent/Mutex 配对"。

本仓当前的闸是 `ascend_fla/ops/kda/chunk.py` 的 `_check_single_chunk_heads`（`C==1 and B*HV > block_dim` 就报错），
边界逐格钉在 `tests/test_kda_gating.py`。

## 步骤

1. 在 sim 下复现上表，至少覆盖 bd∈{1,2}×HV∈{2,4}，C∈{1,2}，逐头报 `o` 对 CPU 参考的相对 L2。
   sim 复现不了就换 pipesim（它模拟 lowered 事件与 hazard）；都复现不了就说明原因。
2. 给 kernel 的 lowered 事件序列加观测，在你自己的临时副本上加打印或事件记录，不改 ascriptor 仓，
   然后对比"最后一个头"与其他头在 L0C / L1 读写和 DEvent / Mutex 上的差异。
3. 确切指出缺的是哪一次同步：哪个事件、哪一行、为什么 C≥2 时被补上。
4. 写出修补方案的 diff 放进报告里，不要应用，并说明如何在 sim 下证明修好：上表全格变对，C≥2 结果逐位不变。
5. 同样的构造在 a2 profile 下是否同样出错，这是给 A2-03 的依据。

## 已知陷阱

**按规律瞎改可能让 case 变绿而原因没除**（`AGENTS.md` §6.5）。

`bd=1` 与 `bd=N` 输出应逐位相同，切分不改算式。这是不需要参考的硬判据，可以拿来交叉验证。

两个维度各自全绿不代表组合全绿：要扫 (C, HV, bd) 的组合边界，不是单轴。
