## 这条任务是怎么来的

issue #71：GD2-03（`0397aa1`→`d44df9e`）合入后，同一 assignee 继续做第二轮优化——
WY stage 的行对复用，减少重复 UB 加载与行间发布屏障，乘法/减法顺序不变。范围与 GD2-03
完全一致（同一份写集、公开 API/精度/预算/5-launch 结构不变），只是 GD2-03 那次的 PR #67
已经合入关闭，continuation 不能挂在旧 PR 上，所以另开一条任务号。

**这条与 GD2-03 一样，是对已批准边界（D-PM-16）的延续，不是新的范围决策**——但按看板自己的
`_check_origin` 规则，外部 REQUEST 来源的任务在用户明确批准前只能是 `gated`，机制上不允许
PM 自己放行，即使内容判断上没有异议。

## 步骤

同 GD2-03 的方法论，换成 WY stage：

1. 对 `690f420`（GD2-03 验收版本）先做 T=4096/T=1024/H=16 的 stage 级 + 调用级基线 profile。
2. 一次只改 WY 一处（行对复用，减少重复 UB 加载与行间屏障），累加/乘减顺序不变。
3. 每次改动后重跑：12 契约 case 在 bd∈{1,8} 全过、13 个 stage tensor 逐位相同（跨 block_dim
   且相对 `690f420` 基线）；静态检查、缩小形状 sim/pipesim（含奇数尾块、多头复用两类边界）、
   真机 board source 复验、223 项 host suite 全部重跑，不是复用 GD2-03 时的旧记录。
4. 性能验收：三轮同步三明治，对 `690f420`（本轮基线）与 `0397aa1`（GD2-01 原始基线，累计增益）
   两个都要报——issue #71 已经给了初步数字（增量 T1024 14.5~14.7%/T4096 15.1~15.9%，
   累计对 `0397aa1` 21.8~22.0%/23.3~24.0%），DONE 里要交付这两组数字的最终版本，
   连同 CPU golden 通过、byte-equality 前置检查。
5. 负结果同样要留：如果某个行对复用方式没有稳定通过某个长度，保留对照，不要只留成功版本。

## 验收

- [ ] `690f420` 基线的 stage 级 + 调用级 profile 数字。
- [ ] 候选改动前后对照齐全（不是只报最终版本）。
- [ ] 12 契约 case 在 bd1/bd8 全过，13 个 stage tensor 跨 block_dim 与相对 `690f420` 逐位相同。
- [ ] 精度判据不变：1e-4 dual-oracle 预算，`223 passed / 5 skipped`（含 FLA oracle）。
- [ ] 性能数字两组：对 `690f420` 的增量、对 `0397aa1` 的累计，两个长度都要一致变快。
- [ ] `contract.json` 用独立的 baseline/candidate SHA256 区分版本，`validation.hardware`
      如实更新（参照 GD2-03 的做法，不要退回旧的笼统写法）。
- [ ] `git diff --stat` 对 `reserved_paths` 为空；公开 API 签名不变。
- [ ] SoC + CANN 版本 + opp 算子包随每个真机数字一起报（PROTOCOL §3.7）。
