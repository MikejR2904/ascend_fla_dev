## 2026-09-19 更正与追加（A2-03 申领人的只读探针 + PM 核实；先读）

- **「派生」不是换 import。** pin 版库的 `ascriptor.a2` facade 没有 `@vf` / `@simt`（`ascriptor/a2.py:6,18` 明写，`__all__` 里把 `vf`、`simt` 排除；PM 读源码核实）：a2 上向量侧是 UB 指令，不是 a5 的寄存器形式。
  申领人探针（自述）：15 个 KDA kernel 里 14 个用 `@vf`，把 a5 源码的 import 换成 a2 后 5 个前向 kernel 全部在加载时 `NameError: vf`；a5 KDA 的 cube↔vector 交接是 UB→L1 直写，而库里现有的 A2 attention 单元走 GM workspace。
  所以这条任务要**重写全部向量侧与数据流**，本规格原来的「派生」措辞与 20h 时限都是低估。**第一个 `STATUS` 必须给按 kernel 的工作量估计**，PM 据此调整时限、必要时把任务拆开；不按 `timebox-slip` 扣分。
- **真机验证（用户 D-PM-34）**：在申领人自己的 a2 真机（910B3 / CANN 9.0.0）上验证，结论只对那一套成立；A2-11 之前 A2 数字只作观测（`AGENTS.md` §2）。
- **A2-01 的结论落地**：所有写同一块 L0C 的累加链显式 `barrier(Pipe.M)`、不分 dtype；BF16/FP16 的 `splitk` 不用 `M<64` 的形状，入口按 §7 报错（见下面「已知陷阱」里的线索与 `gaps.json` 的 `a2-splitk-*`）。新建的是**新单元**（`kernels/projects/a2/**`），不改上游与 A5 源码——这不属于 kernel 批次。
- **D-PM-35 / D-PM-37**：BF16 的 kernel 直接吃 BF16、写 BF16，dtype / 格式转换都在 kernel 里；既然向量侧要重写，**a2 单元的公共 ABI 直接按 token-major 直读直写设计**，别重蹈 A5 在 host 侧 `permute().contiguous()` 的覆辙（见 `docs/pm/bf16-kernel-side.md`）。

## 目标

在本仓 `kernels/projects/a2/` 下按 ascriptor 的 unit 协议建出 KDA 全链路单元，A2 真机一到就能直接进
A2-12～A2-14：

| 本仓 a2 单元 | 来源 |
|---|---|
| `kda_fwd_stable` | 上游 `a5/kda_fwd` 五个 kernel，其中 gate / intra / wy 取本仓 `a5/kda_fwd_stable` 的改写 |
| `kda_bwd_stable` | 上游 `a5/kda_bwd` 九个 kernel，其中 finalize_pre / finalize_post 取本仓 `a5/kda_bwd_stable` |
| `kda_fused_recurrent` | 本仓 `a5/kda_fused_recurrent` |

顺带把 a2 这边的 `stable-unit-no-harness` 一起解决掉：每个单元都要有 `unit.py`（导出 `make_inputs` /
`reference` / `execute`）加 `contract.json` 加 `run.py`，能被 harness 独立运行。

## 背景（摘录）

`AGENTS.md` §3 定的规矩是不修改 ascriptor 仓，要改 kernel 就在本仓按 unit 协议建自己的单元。

a5 单元 `contract.json` 里的 `block_dim` 上限、门控 `recommended_limit`、`accuracy_vs_span` 全是 A5 实测值，
不能原样写进 a2 契约。a2 契约里这几个字段标 `untested` 或待真机，限值留空或者取保守值，并注明来源。

A2-01 会给出一张命中表。命中 split-K FP32 构造的 kernel 在本任务里不改算式，只在契约与 README 里标注，
按 A2-01 的推荐方案留好接口；真正的改写归到 kernel 批次 A2-K1。

还有个已知的静默缺陷 `c1-multihead-o-corrupt`，它在 `kda_sub45_fused_kernel` 里，派生过来会一起带过来
（A2-04 正在定位）。

## 已知陷阱

模拟器通过不等于真机通过，Gemini 文档里也提到仿真器不严格模拟 DMA 时序 —— 所以契约不许往 board 上写 passed。

标量名以 `CompiledKernel.scalar_names` 为准。aclnn HostSpec 标量包含 GM 形状里的全部符号维，`kda_bwd` 因此多一个 `T`。

**线索（2026-09-19，A2-01 的 `RISK silent-wrong-result`，申领人自述 + PM 只核了静态部分，A2-01 的 DONE 证据到了才生效）**：ascriptor pin 里 M10-081 的 settle 规则只在 a2 系且 A/B 都是 FP32 时给 split-K 插 `PIPE_M`
（PM 已读 `desugar.py:411` 核实，注释写明其他 dtype 不在范围内）；申领人在 910B3 / CANN 9.0.0 真机上报告 **BF16/FP16 的 `splitk` matmul 在 M16 上输出有限但全错、M32 触发 AI Core 异常**，模拟器与 pipesim 看不出。
所以 a2 派生单元里凡是写同一块 L0C 的累加链（`splitk` 与手写 MMAD 链）都要**显式 `barrier(Pipe.M)`、不分 dtype**；在这条被证伪或被上游修好之前，a2 路径不用 `M<64` 的 BF16/FP16 `splitk`，入口按 `AGENTS.md` §7 显式报错。
KDA 的 BF16 kernel 里有 BF16 累加链（命中表里的 recurrent），正是本任务要派生的对象——**逐个核对，别照搬 a5 的写法**。这只是观测（A2-11 之前 A2 数字不构成算子结论）。
