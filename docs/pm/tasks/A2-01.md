# A2-01 定性 ascriptor 的 split-K FP32 cube 数值缺陷（a2 profile）

- 波次 / SoC：W0 / a2。纯主机侧，跑 `ascriptor check` / sim / pipesim，不需要 NPU
- 优先级：P0 · 时限：12h · 依赖：无
- 需要：ascriptor workspace（按它的 `agent/compatibility.json` 选 library/kernels 修订，DONE 里写明修订号）
- 写集：`benchmarks/a2/repro_splitk_fp32.py`、`benchmarks/a2/README.md`
- 证据目录：`tmp/A2-01/`（不提交）

## 为什么是 P0

2026-09-14 定下首波在 A2 上做算子与整模型（见 `AGENTS.md` §2）。而 ascriptor 侧在 2026-09-06 把 A2/A3 标成
deferred（`docs/matrix/ops.json` 的 `ascriptor_pin.release_scope`，决策号 D-250），还附带一个没解决的
split-K FP32 cube 数值缺陷。这东西没搞清楚之前，A2 上任何算子结论都不可信，所以 A2 的算子任务全都挂在本任务下面，
真机复现留给 A2-11。

## 背景（摘录，任务自包含）

本仓在 A5 上跑通的 KDA kernel 链是这样的：前向 5 个来自上游 `kernels/projects/a5/kda_fwd`，其中 gate / intra / wy
三个被本仓的 `kernels/projects/a5/kda_fwd_stable` 替换（门控跨度的数值稳定改写）；反向 9 个来自上游 `kda_bwd`，
finalize_pre 与 finalize_post 被 `kda_bwd_stable` 替换；decode 那 1 个是本仓自写的
`kernels/projects/a5/kda_fused_recurrent`。
GDN 那边是上游 `gdn_fwd` / `gdn_bwd`，五个阶段 preprocess / inverse / recompute / scores / recurrent。

"split-K" 具体指什么，先去 ascriptor 侧的记录里查实，别按字面猜 —— 它可能指 K 维被切给子核、cube 按 K 分块，
也可能是别的东西。

## 步骤

1. 在 ascriptor workspace 里找到缺陷的原始记录（`agent/` 下的决策、handoff、issue，以及 D-250 相关条目），
   摘出现象、复现形状、已知或怀疑的根因、当初为什么 defer。
2. 查实 ascriptor 的 a2 profile：名字、cube 与 vec 核数、UB 容量、支持的 dtype，并记下来源文件与行号。
   A5 上 profile 声明 32 cube / 64 vec 而物理只有 28 / 56，超出会在 barrier 上死锁；a2 有没有同类出入，
   本任务只能从文档查，真机确认是 A2-10 的事。
3. 写最小复现 `benchmarks/a2/repro_splitk_fp32.py`，CPU 参考对 sim；缺陷若与流水或同步有关，再加 pipesim。
   用 `--profile a2|a5` 参数化，同一个 kernel 在 a5 profile 下作对照组。
4. sim 和 pipesim 都复现不出来的话，给出论证（比如缺陷只在 CANN 编译或硬件执行时才出现），
   并在同一个脚本里备好 `--launcher aclnn` 的真机复现入口，留给 A2-11。
5. 把 KDA 的 15 个和 GDN 的 10 个 kernel 逐个扫一遍，判定有没有用到触发构造。要逐个列出来
   （kernel、文件、行、命中还是未命中、理由），不要写"其余类似"。
6. 列候选绕行方案：改写避开该构造、换 dtype、建派生单元、或者按 `AGENTS.md` §7 装闸报错。每个方案配一份 fp32 下的数值验证计划。

## 已知陷阱

`AGENTS.md` §6 讲"按量程失效的缺陷要把整条链同类算式列一遍"，构造型缺陷同理：修一处不等于修完。

A5 上的门控上限、`block_dim` 上限、核数都不是 A2 的预期，照搬就是 `soc-assumption`。

下结论要读未过滤的原始日志。CANN 和模拟器可能打出不带换行的噪声，粘在下一行前面。
