# A5K-02 KDA Aqk 修复接入公开调度（`ops/kda/chunk.py`）

- 波次 / SoC：W0 / a5 —— A5K-01（D-PM-21）的自然延续，不是新的 KDA-on-A5 范围
- 优先级：P1 · 时限：16h · 依赖：A5K-01（已完成）
- 需要：A5 真机（同一份已配置访问）、ascriptor workspace
- 写集：`ascend_fla/ops/kda/chunk.py`、`tests/test_kda_gating.py`、
  `tests/test_kda_aqk_dispatch.py`（新文件）、`kernels/projects/a5/kda_fwd_stable/**`、
  `docs/research/kda_aqk_handoff_repair.md`、`benchmarks/verify_kda_aqk_public.py`（新文件）

## 这条任务是怎么来的

A5K-01（PR #78，已合入）把 A2-04 诊断出的 Aqk 交接缺陷修好了，但**只在派生单元
`kernels/projects/a5/kda_fwd_stable/kernels/recurrent.py` 里**——`ops/kda/chunk.py` 不在
A5K-01 的写集内，公开调度 `chunk_kda_fwd` 至今仍然选择原始（有缺陷的）recurrent。
`gaps.json` 的 `c1-multihead-o-corrupt` 条目已经写明这是个未解决的边界：**在这条任务
完成之前，公开 API 的用户仍然会撞上真机确认过的奇数 C≥3 静默错误**。issue #79 提议把
这个洞补上。

## 一个已知的、需要小心处理的细节

A5K-01 自己的验证脚本 `kernels/projects/a5/kda_fwd_stable/repair_runtime.py` 里，
`selected_kernels("baseline")` 直接返回 `kda_fwd_kernels("stable")`（即公开调度当前用的
那份），**没有做任何覆盖**。这在 A5K-01 完成时是对的——那时候公开调度还是原始版本，
`baseline` 变体天然就是"原始"。但**一旦本任务把公开调度切换成修复版，`baseline` 就会
悄悄变成修复版**，A5K-01 保留的负对照（用来证明"不修复就是错的"）会失去意义。

**本任务必须同时更新 `repair_runtime.py`**（属于 A5K-01 的写集 `kda_fwd_stable/**`，
本任务写集里已包含），让 `baseline` 变体显式钉死指向未修改的原始 recurrent 源码
（比如直接引用 `benchmarks/diag_c1_multihead.py` 里已经有的 `upstream` 变体加载方式），
不要依赖"公开调度现在指向什么"这种会变的东西。

## 步骤

1. **在 `ops/kda/chunk.py` 的 `kda_fwd_kernels("stable")` 里选定修复版 recurrent**——
   这是本任务唯一要动公开调度的地方。搞清楚原来的选择逻辑（可能是按文件名/函数名硬编码，
   也可能是个查找表），把 `kda_fwd_stable/kernels/recurrent.py` 的
   `kda_sub45_aqk_repaired_kernel` 接进去。
2. **门控**：修复版只在"奇数 C 且重复头"这个具体域上跟原版行为不同（其它情况逐位相同，
   A5K-01 已经验证过）。如果修复版对某些从未测过的组合没有把握，门控要显式拒绝，
   不要隐式放行。原始未修改版本作为诊断基线保留可调用（不是公开路径），不删除。
3. **修复 `repair_runtime.py` 的 `baseline` 变体**（见上一节），让它显式钉住原始源码，
   不再间接依赖 `ops/kda/chunk.py` 现在选了什么。
4. **真机验证走完整的公开 API 路径**（不是像 A5K-01 那样调用派生单元的独立入口）：
   `chunk_kda_fwd` 与"带 cache 的前向"路径都要测，覆盖 C=1..6 × GQA × state × bd=1..4 的
   完整网格，对同样的两个独立 CPU FP32 oracle，预算不变（.02/.02/.05）。
5. **偶数 C 与未受影响的缓存中间量要逐位不变**——这是回归判据，不是新功能的验收判据。
6. **性能三明治测的是公开路径的实际延迟**（不是派生单元的 timing），CPU golden 依然
   只做正确性、不做性能基线。**这个任务的目的是正确性，不是性能**——不设新的加速目标，
   如果修复版比原版慢也要如实报，不必也不应该为了"看起来更好"去优化。
7. `test_kda_aqk_dispatch.py`（新文件）：专门测"公开调度确实选中了修复版"这件事本身——
   这是最容易被将来的重构悄悄破坏的一条，值得有一个独立测试盯着，不要只混在功能测试里。

## 验收

- [ ] `chunk_kda_fwd` 与带 cache 的前向路径都选中修复版 recurrent；不支持的组合在真正
      发射 kernel 之前就报错。
- [ ] 完整真机网格（C1-6 × GQA × state × bd1-4）通过公开 API，对两个独立 oracle，
      预算不变，逐头/逐 chunk 报数字。
- [ ] 偶数 C 与未受影响的缓存中间量逐位不变；修复结果跨 bd 一致。
- [ ] A5K-01 的负对照（original/qg-only）与缩小诊断保留，且 `repair_runtime.py` 的
      `baseline` 变体在公开调度切换之后仍然指向真正未修改的原始源码。
- [ ] 三轮同步三明治测的是公开路径延迟，不设性能目标，如实报数字。
- [ ] host tests、公开调度选择测试、canonical runner、隐私扫描全过。
- [ ] `docs/matrix/*.json`、`docs/handoff.md`、`docs/pm/*` 不在本任务写集内——PM 合入后统一改。

## 已知陷阱

- 不要把这条任务做成"顺便扩展 KDA-on-A5 的范围"——这是完成 A5K-01 已经承诺的收尾，
  不是启动新的 KDA-on-A5 工作。`A5-01`..`A5-06` 的 `gated: wave:W-A3` 不受影响。
- 见上面"已知的、需要小心处理的细节"——这个坑很容易漏，`baseline` 变体悄悄失去意义
  不会报错，只会让下一个人复现负对照时以为验证过了实际没有。
