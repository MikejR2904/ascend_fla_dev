## 这条任务是怎么来的

A2-03 / A2-09 在申领人的 910B3 上用 ascriptor 自带的 **aclnn launcher**（落盘 + 独立进程，是 kernel 开发 / 验证框架）跑通了 a2 单元；
本仓真正要交付的是 **runtime 桥**（`AGENTS.md` §4）：把 kernel 编成常驻 CANN 自定义算子 `.so`，经 `torch.library` 在进程内直吃 NPU device tensor。
桥在 A5 上已经通了，但**从没在 A2 上跑过**；A2 的内置算子包覆盖、CANN 版本、核数 / UB / `block_dim` 上限也一个都没有官方数字（A2-03 只顺手测到「cube / vec 核数 20 / 40」这类自述）。
本任务补上：在 A2 上把桥跑起来，并证明它与已经验证过的 aclnn harness **逐位一致**。

## 范围

1. **环境与内置算子包覆盖（实测，报数字）**：SoC 名、CANN 版本（**带 inner / compiler 时间戳**，见 BF-02 观察：同为「CANN 9.2.0」的不同小版本头文件不同）、`ls $ASCEND_OPP_PATH/built-in/op_impl/ai_core/tbe/kernel/`
   的目录列表、`torch_npu` 的计算算子可用面（`randn` / `zeros` / dtype 转换 / `contiguous` / matmul / einsum / cumsum / `empty` / H2D / D2H / 跨步 D2H 的 `Slice`…）逐项试并记通过 / 失败与报错原文。
   **不许把 A5 机器的结论搬过来**（`AGENTS.md` §6「结论不跨 SoC 继承」）。
2. **runtime 桥在 A2 上通**：用桥（`compile_kernel(..., device="a2", backend="cce")` 一类入口，A2-02 落地后用 `platform` 解析）把 A2-03 合入的两个单元
   （`kda_fwd_stable` 的五个 kernel 与 `kda_fused_recurrent`）编成常驻 `.so`，**进程内**调用、直吃 NPU tensor、零拷贝。一个进程一份 build、一个算子名一个 vendor 树（`AGENTS.md` §6 铁律二）；
   所有要用的 kernel 在第一次执行前编完（`ASCEND_CUSTOM_OPP_PATH` 只读一次）。
3. **对 harness 逐位一致**：两个单元的全部契约 case（fwd 20、decode 8，`bd ∈ {1,2}`）用桥跑出的输出，与 A2-03 evidence 里 aclnn launcher 的输出**逐位相同**（不是相对 L2：同 kernel、同输入，字节必须一样）；
   任何一个 case 不一样都是桥或 launcher 有 bug，如实报、不要解释掉。
4. **设备事实（只作观测）**：cube / vec 核数、UB / L1 / L0C 容量的实测、`block_dim` 在 1、2 之外**能不能跑**——超物理核数会在硬件 barrier 死锁，所以**每个 `block_dim` 单独进程、带超时、先小后大**，
   一旦死锁不要重试，记下就停，留一个现象说明（不是 A2 的上限结论）。

## 已知陷阱

- `torch_npu` 在缺内置算子包的机器上，取值 / 比较 / layout 重排要先 D2H 再做，且**先整块 D2H 再切**（`AGENTS.md` §5）；A2 上要重新实测哪一条成立，别照抄。
- aclnn HostSpec 的标量列表含 GM 形状里的全部符号维，标量名以 `CompiledKernel.scalar_names` 为准。
- A2 上的库约束（无 `@vf`、无 `dma.ub_to_l1` / `dma.l0c_to_ub`、c220 无 FP32 L0C→L1、`dup` 无 BF16）见 A2-03 的 README；桥不该绕开它们。
