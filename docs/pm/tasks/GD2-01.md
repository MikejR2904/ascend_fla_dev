# GD2-01 GDN-2 chunk 前向：量程设计 + 独立 kernel 单元（主机侧，只做 forward）

- 波次 / SoC：W0 / a5。纯主机侧：量程调研、ascriptor check、reference、sim。真机数从 GD2-02 起
- 优先级：P1 · 时限：24h · 依赖：无
- 需要：ascriptor workspace（见 `AGENTS.md` §3 的 gitcode 来源）
- 写集：`kernels/projects/a5/gdn2_chunk_fwd/**`、`ascend_fla/ops/gdn2_chunk_fwd.py`、
  `tests/test_gdn2_chunk_fwd.py`、`docs/research/gdn2_chunk_fwd_gate_range.md`

## 这条任务是怎么来的

用户 2026-09-17 批准了一条外部 REQUEST（issue #61，来自 limjiunnbin 账号，自述是"the implementing
agent using limjiunnbin"，即另一会话里用该账号运作的 agent）：实现 A5 上的 GDN-2 chunk 前向
（长 prefill 用，含 prefill→decode 的 state 交接），forward-only，不碰 backward / A2 / A3 /
FLA dispatch 注册 / ascriptor 本身。

`gaps.json` 的 `gdn2-abi-not-gdn` 早就记着这正是剩下的阻塞项：GDN-2 的 recurrent 那一半
（`a5.gdn2_fused_recurrent`、`a5.gdn2_fused_decode`）已经做完并在真实 95B 权重上验证过，
**剩下 T>16 的长 prefill 与训练反向仍缺 `gdn2_chunk_fwd_bwd`**。本任务只做前向那一半。

## 为什么不是简单照抄 KDA 的 chunk 算法

**GDN-2 的门控跨度比 KDA 大一个数量级，而且 ABI 本身也不同，两条都不能照搬：**

1. **跨度**（`gaps.json` 的 `gdn2-chunk-gate-range`，P1）：2026-09-14 用真实 95B checkpoint
   （`B=1/T=4096`、seed=20260914 的合法 vocab 随机输入）逐层测过，**64-token 局部累计衰减跨度
   最大 1461.214**，18 层均值 69.041，完整 4096-token 跨度最大 83768.180。
   KDA stable chunk 已验证的跨度只到前向 155、反向 105 —— **远远不够**。
   `kernel_change_note` 写死了一条硬规矩：**禁止直接复制 KDA stable 的 105/155 跨度实现。**
   AGENTS.md §6 那次 KDA 门控跨度的教训（改锚点到中点只把可用量程翻倍）在这里不管用 ——
   1461 / 2 还是远超任何 fp32/bf16 能扛的 `exp(±span/2)`，**必须做分段 / 归一化表示，
   不是重新选个锚点**。
2. **ABI**（`gaps.json` 的 `gdn2-abi-not-gdn`）：现有 `a5.gdn_fwd` 只接受 per-token 标量
   `beta`/`g`；GDN-2 的 `g`（衰减）、`b`（key-channel erase gate）、`w`（独立的 value-channel
   write gate）都是 **channel-wise**（形状 `[B,T,H,128]`），是一个新 ABI，不是 GDN 的改名。
   `a5.gdn2_fused_recurrent` 已经按这个独立 ABI做完，本任务的 chunk 版本要跟它的语义对齐
   （token-major、q/k L2 norm 在 kernel 内做、K-major state），但**不能直接搬它的代码** ——
   recurrent 与 chunk 是两种算法结构。

## 目标模型的真实形状（`docs/matrix/models.json` 的 `gdn2-1.3b-fineweb-edu-100b`）

`H=HV=16`（无 GQA 分组，`head_group_ratio=1`，比 GDN 简单）、`K=V=128`、`context_length=4096`、
BF16。checkpoint 与 tokenizer 来源见 models.json，已完整记录 URL/revision/sha256。

## 步骤

1. **先做量程调研，再写 kernel 算式**（`gdn2-chunk-gate-range` 的 `proposed_action` 原话）：
   把 forward 全链路里所有 `exp(g_i - g_j)` 形状的算式逐处列出，按 `{4, 8, 16, 32, 64}`
   五档子块大小扫实测量程 —— 用与 2026-09-14 那次相同的方法（真实 95B checkpoint、
   `T=4096`、合法 vocab 随机输入）复现 1461.214 这个反例，再额外测一段自然文本样本
   （不能只用随机输入下结论）。对每档子块给有限性与精度（对 fp32 recurrent oracle 的
   相对 L2）两条曲线，闸按更严的那条定（AGENTS.md §6 的方法论原样搬过来）。
   结论写进 `docs/research/gdn2_chunk_fwd_gate_range.md`：选哪档子块、什么数值表示
   （分段 / 归一化，不是简单端点或中点锚），为什么。
2. 按 ascriptor 的 unit 协议在 `kernels/projects/a5/gdn2_chunk_fwd/` 建单元
   （`unit.py` 导出 `make_inputs/reference/execute` + `contract.json` + `run.py`）。
   `contract.json` 的量程限值就是第 1 步的结论，不是从 KDA 抄一份改改数字。
3. 写 `ascend_fla/ops/gdn2_chunk_fwd.py` —— **独立的、显式 opt-in 的新模块**，
   不是 `ascend_fla/ops/gdn2/` 包下的文件（那个包整体是仓主并行轨道的 reserved path，
   见下一节）。对外接口参照 `ascend_fla/ops/gdn2/fused_recurrent.py` 的风格
   （token-major、显式 `prepare()`、不满足定尺就报错，不做隐式兜底）。
4. 跑 `run.py reference` / `run.py sim`：契约 case 之外，额外覆盖真实模型形状
   `T ∈ {1, 16, 63, 64, 65, 127, 128, 192, 320, 1024, 4096}`（含 chunk=64 边界与
   1461 反例落在的那个 64-token 窗口）、零/非零 initial_state、奇偶 chunk 数、
   `B*HV` 与 `block_dim` 的边界组合（参照 AGENTS.md §6 "形状维度要逐格扫"，
   不要只扫单轴 —— `c1-multihead-o-corrupt` 就是扫漏了 (C,HV) 组合点吃的亏）。
5. 双 oracle 交叉验证：
   - 对 `ascend_fla/reference/gdn2.py` 的 FP32 recurrent（**只读**，见下一节的边界）：
     `o` 与 `final_state` 相对 L2 ≤ 1e-4，报 `max_abs_diff`。
   - chunk 与逐 token recurrent 数学等价（AGENTS.md §6：这是不需要参考的硬判据）：
     至少一个 toy 形状 + 一个真实形状，逐位或按预算一致，如实说明是哪种。
6. 门控：不满足定尺（形状、dtype、chunk 边界）时 `ascend_fla.ops.gdn2_chunk_fwd` 显式报错，
   报清楚哪一条不满足、实际值是多少（AGENTS.md §7）。绝不静默退化到逐 token 或 torch 兜底。

## 已知陷阱

- **门控跨度不是"选个锚点"能解决的**，1461 比 KDA 的可用域大一个数量级，参照第 1 步。
- **GQA 不是问题**（`head_group_ratio=1`），但**channel-wise 门控是** —— 不要照搬
  `a5.gdn_fwd`/`a5.gdn2_fused_recurrent` 的标量门控假设。
- 形状扫描要覆盖 `(T, block_dim, B*HV)` 的组合边界点，不要只扫单轴（AGENTS.md §6）。
- `ascend_fla/reference/gdn2.py` 只读：`import` 它做 oracle 完全可以，改它不行。
- 不要把这个任务做成"顺便把 layer 接上" —— 接线是仓主轨道的事，见上一节。
