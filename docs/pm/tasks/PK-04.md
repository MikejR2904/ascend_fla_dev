## 已知陷阱

- PK-02 里"A 相对 L2 为 0"**只对 CPU 模型成立**（参考与 kernel 的 ATK 都是与 naive 同顺序的 FP32 逐元素运算）；真机的 `exp/ln`
  不保证逐位相同，预算仍是 ≤ 1e-4，别拿"逐位相同"当真机的期望。
- 跨度 4096 的 FP32 前缀差抵消误差 S=1.34e-4 超预算，已保留在公开域之外（门控 155）；不要因为真机上某个 case 通过就放宽门控。
- **已知候选缺陷（验收必须覆盖）：`prepare` 的门控前缀和**。若它是纯 FP32 顺序累加，在「每 chunk 首项 ≈ −155、其余 ≈ −1e-5」这类**域内**
  （跨度 < 155）对抗门控上会系统性偏离高精度累加：`ulp(155) = 1.526e-5`，−1e-5 的加数每步被舍成 1 ulp，64 项累计偏差 3.36e-4
  （PM 用 numpy 独立复算：纯 FP32 顺序累加对高精度累加再舍成 FP32 的最大偏差是 0.000335693359375）。申领人自述真机上它让公开 API 的
  `o` / `S` 相对 L2 到 1.30e-4 / 1.82e-4，超出 ≤ 1e-4 预算（PM 未复现，以 DONE 里的原始日志为准）。所以「域内对抗性跨度」**不能只测平滑或随机门控**；
  `bd=1..4` 逐位相同**发现不了**它（各 bd 共用同一累加）。**修法不预先批准**：先用有界诊断定位到确切原因，再在已批写集内修
  （申领人提议的补偿累加只是候选）；修不了就把门控收到有实测依据的位置，**闸是双边约束**（`AGENTS.md` §6）。
  这个模式是否同样打到 KDA 链路（同类前缀和）未知，**不在本写集**：发现相关证据只发 `RISK`，不要顺手改。
