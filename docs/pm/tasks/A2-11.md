## 这条任务是怎么来的

`AGENTS.md` §2：ascriptor 库里 M10-081（A2 系上两次短 MMAD 写同一块 L0C，硬件不互锁，第二次读到没落定的累加器）在 pin 版里对 FP32 split-K 有自动修复（`desugar.py:411`），
**BF16 / FP16 split-K 与 FP32 手写累加链没有**。A2-01 在 910B3 上做了刻画（自述：BF16 / FP16 split-K 在 M16 输出有限但全错、M32 触发 AI Core 异常；FP32 手写链「时序没踩到」、未复现出错）。
A2-03 / A2-09 的 a2 单元按结论**所有 `is_init=False` 累加前显式 `barrier(Pipe.M)`、不用 M<64 的 BF16 / FP16 split-K**。A2-11 要回答：**这些绕行在真机上够不够？**
在它给出证据、且用户认可之前，A2 上任何算子结论都只作观测。

## 范围

1. **最小复现（三类，各自独立进程，每个 case 重复 ≥ 1000 次并加时序扰动）**：① FP32 split-K（pin 已修）——确认修复在真机上逐位稳定；② BF16 / FP16 split-K（M16 / M32 / M64）——复现或否定 A2-01 的自述，报错误形态、出错频率与 AI Core 异常的报错原文；
   ③ FP32 手写累加链（`is_init=False`，无 barrier）——能不能在真机上踩出错误，报频率；踩不出要如实说「未复现」，**不是「不存在」**。
2. **绕行验证**：同样三类，加上显式 `barrier(Pipe.M)` 的版本，重复 ≥ 1000 次 × 多个 `bd` × 多张卡（机器与卡归你自己管，D-PM-28）：输出必须**逐位稳定**；去掉 barrier 的负对照如实报（踩不出错也要报，说明「保守保留」的理由）。
3. **对已合入的 a2 单元做机械检查**：一个静态测试 `tests/test_a2_accumulate_barriers.py`（AST 级）——`kernels/projects/a2/**` 里每个 `is_init=False` 的 matmul 之前都紧邻 `barrier(Pipe.M)`、不使用 BF16 / FP16 的 `splitk`（M<64），
   以后有人改 a2 单元时它会红；A2-03 评审时我手工做过这件事，这条把它固化。
4. **建议（不是决定）**：`docs/research/a2_splitk_gate.md` 里写清——哪些构造已证实安全、哪些只是「未复现」、哪些必须永远显式禁止 / 报错（`AGENTS.md` §7），并给出「A2 结论算数」需要满足的条件清单，由用户裁定。

## 已知陷阱

- 时序类缺陷「没踩到」≠ 安全（A2-04 的教训：症状规律会伪装成结论）。所以要有次数、扰动方式与负对照，别用一次通过下结论。
- 死锁 / AI Core 异常会占住卡：每个复现单独进程、带超时，出异常就停，不要循环重试；别碰别人的进程。
- `gaps.json` 的 `a2-splitk-fp32-cube`、`a2-splitk-bf16-fp16-unsettled` 是本任务的输入，别把自述当已证实。
