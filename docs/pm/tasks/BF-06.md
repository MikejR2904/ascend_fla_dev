## 2026-09-19 追加（用户 D-PM-37）：格式转换也在 kernel 内，FP32 路径同样

现有 decode 入口的 host 转换（`.to(torch.float32)`、`permute(0,2,1,3).contiguous()` 重排、beta 的重排等）**两条 dtype 路径都要去掉**：kernel 直接读 token-major、写 token-major；FP32 路径输出改前改后逐位相同。
不得为了省事在 host 留一处「布局适配」。两条路径都过 host 算子审计。

## 2026-09-20 裁定（PM，依申领人在 #105 的 `RISK contradicts-handoff`；PM 核实矛盾成立）

矛盾是我写的：「范围」一节说 A2-44 的 raw flags 预处理仍走 host、融合归 BF-07、本任务不改；而 D-PM-37 追加段与通则要求两条 dtype 路径都没有 host 转换 / 算术。`ascend_fla/ops/kda/chunk.py::_prepare_inputs`
（`use_*_in_kernel=True` 时的 q/k l2norm、门控 softplus·exp、beta sigmoid，外加 `.to(qk_dtype)`）确实是产出进入计算的张量的 host 算术，不是只读校验。裁定三条：

1. **raw flags = True 的分支：存量例外，围起来、单列、不扩大，不宣称合规。** 该分支保持现有 A2-44 行为**不动**（BF-06 不改 `_prepare_inputs`，也不往里新增任何 host 操作），
   在 host 算子审计里**单列一类**「已登记的存量例外 → BF-07」，文档里写明「本分支的 host 预处理未消除，消除它要改已有派生单元的 kernel，属 BF-07，需要用户的 kernel 批次批准」。
   **默认 flags 全 False 的路径必须完全合规**（真机审计只有 `aten.empty` / `aten.view`，两条 dtype 路径都是）。这不是给新代码开例外：BF-06 自己写的入口与 kernel 里没有一处 host 转换 / 算术。
2. **dtype 域：BF16 q/k/v + FP32 g / beta / state，或全 FP32；其余一律显式报错并说清约束。** 原 wrapper 收「任意浮点 dtype」全靠 host `.to(torch.float32)`（原 kernel 契约其实只有 FP32），
   D-PM-37 禁止的正是这种 host dtype 转换，所以 FP16 / FP64 / 混用 dtype 只能显式拒绝，不能再悄悄加宽。这是 D-PM-37 的直接后果、不是数值域收窄；**PM 会把它记进决策并告诉用户**。
   如果仓里已有测试 / layer 在用 FP16 / FP64 decode，先发 `RISK` 说明具体调用点，别自己改用法。
3. **block_dim 不收窄**：原 FP32 支持 `{1,2,4,8,16,28}`，全部保持，并补新路径的真机回归（每个 bd 单独进程）。验收：`bd ∈ {1,2,4}` 跑完整网格；`bd ∈ {8,16,28}` 至少跑完整 workload 加一组边界 case，
   FP32 改前改后逐位对照在六个 bd 上都做（可用较小的 case 集）；BF16 新路径若在某个 bd 上做不到，**先问用户**（那是比 FP32 窄的域），不要自己缩。
   默认 flags=False 的 CPU 精度校准可以马上推进；受 raw flags / dtype 裁定影响的入口分派，按上面三条落地即可，不需要再等。

## 2026-09-20 prefill→decode 比较口径（PM 裁定，依申领人在 #105 的 `RISK contradicts-handoff`；实现前 / 真机运行前定死，事后不得放宽）

规格里的硬判据只写了「对得上」，没有数。申领人指出得对：BF16 chunk（`kda_fwd_stable`）的 `final_state` 本身带 BF16 WY / cube 的误差（现有契约 rtol=atol=0.02、relative L2 ≤ 0.05，实测 o 约 3e-3），
不能把它当成全序列 CPU FP32 的精确前缀状态。**分三层，全部保留、分别报告，缺一不可：**

1. **decode 自身（严格，不放宽）**：每次 decode 从**实际收到的**硬件 prefill / 前一步 decode 状态起算两个独立 CPU FP32 oracle，`o ≤ min(1e-2, 3F)`、`final_state ≤ 1e-5`。这一层把前缀状态自己的误差隔离掉，只量 decode 的贡献。
2. **分块不变性（逐位）**：一次 decode 16 个 token 与 16 次单 token 串接（状态经 FP32 传递）的 `o` 与 `final_state` **逐位相同**。
3. **端到端（prefill 64 / 128 + decode 64 与同输入一次性 stable 长前向）**：`o` 与 `final_state` 对**两个**全序列 CPU FP32 oracle（pin 版 naive 与独立参考）分别报告，通过线 = **`min(1e-2, 3·E_oneshot)`**——
   `E_oneshot` 是**同一次真机运行里**一次性 stable 长前向对同一个 oracle 的相对 L2（自校准，不引入新的魔法常数）；`1e-2` 是所有 BF 任务共用的 BF16 输出 / 状态上限。
   **不采用**契约里 0.05 那条宽线（它是 A5 继承下来的宽松公共契约，拿来当链的通过线会把差 15 倍的退化也放过）。前缀段（chunk 输出）与后缀段（decode 输出）**各自单列**，各自也要过同一条线；另外单列链输出对一次性长前向的相对 L2 作参考，不设独立门槛。
   `o` 的 `3·E_oneshot ≥ 3F`（BF16 舍入地板是 E_oneshot 的下界），所以这条线不会因为一次侥幸的小 E_oneshot 而误杀。

层 1、2 绝不放宽；层 3 的通过线现在就定死，运行后发现过不了要如实报数并发 `RISK`，**不得改线**。

## 这条任务是怎么来的

用户 2026-09-19（D-PM-35）：BF16 计算必须在 kernel 里做，不能在 host 侧完成；后续 BF16 优先。KDA decode 入口收任意浮点 dtype，但在 host 侧 `.to(torch.float32)` 后进 FP32 kernel（`ascend_fla/ops/kda/fused_recurrent.py`），BF16 计算不在 kernel 里。

## 范围

- 域与现有 decode 一致：`T≤16`、`q,k:[B,T,H,128]`、`v:[B,T,HV,128]`、`g:[B,T,HV,128]`、`beta:[B,T,HV]`、`initial_state:[B,HV,128,128]` FP32（K 在前）；
  BF16 的 `q/k/v` → BF16 的 `o`，`final_state` FP32。kernel 里读 BF16、在 kernel 内转 FP32 做递推（decode 量很小，精度自选，写进文档）。
- 起点（只读）：现有 `kernels/projects/a5/kda_fused_recurrent`（FP32 单元）。新建 `kernels/projects/a5/kda_fused_recurrent_bf16/`。
- A2-44 的 raw flags（`use_*_in_kernel`）预处理仍走现有路径（host 侧 FP32 预处理后再 cast 成 BF16——融合进 kernel 是 `BF-07` 的事），本任务不改它，也不新增 host 转换。
- **prefill→decode 一致性是硬判据**：BF16 chunk 前向（原生 KDA，`kda_fwd_stable`）的 `final_state` 作 BF16 decode 的 `initial_state`，逐 token 递推与一次性长前向对得上。
