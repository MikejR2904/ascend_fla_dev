## 验收

- [ ] **opp 算子包普查**（AGENTS.md §5 开机必查）：记录 `ascend950` 是否在这台机器的
      `built-in/op_impl/ai_core/tbe/kernel/` 里，决定哪些计算能直接在 NPU 上做。
- [ ] `board` / `aclnn` stage 从 `untested` 升级：真机跑通 GD2-01 契约 case 全集，
      逐条给 rel-L2 / max_abs_diff，`bd=1` 与更高 `block_dim` 输出逐位相同
      （AGENTS.md §6 铁律：核切分不改算式，不同就是切分 bug）。
- [ ] 真实 95B checkpoint（`docs/matrix/models.json` 的 `gdn2-1.3b-fineweb-edu-100b`）端到端：
      FP32 logits/cache 预算 1e-3、BF16 预算 1e-2 —— 沿用这个模型现有验证记录已经在用的同一套
      预算（见 `models.json` 该条目的 `validation.cce_full_model`），不要另起一套阈值。
- [ ] **prefill → decode 的 state 交接**：本任务产出的 chunk 前向跑完一段 prefill 后的
      `final_state`，接到仓主轨道的 `a5.gdn2_fused_recurrent` / `a5.gdn2_fused_decode`
      做后续 decode，数值连续（相对 L2 在预算内）。**这一步只读仓主轨道的模块接口，
      不修改它们的文件**——调用即可，不需要写权限。
- [ ] 同卡同步性能三明治：`T ∈ {1024, 4096}`，warmup=10，repeat=50，三轮，
      对 torch_npu 组合实现基线。**两个长度都要一致变快才能报"性能达标"**
      （AGENTS.md §6 铁律一：profile 之前不要相信任何性能推断，这里反过来强调：
      有了 profile 也不能只挑一个长度报喜）。报延迟与 workspace。
- [ ] SoC + CANN 版本 + opp 算子包列表随每个真机数字一起报（PROTOCOL §3.7 DONE 格式）。
- [ ] 没有把这次 A5 机器的任何结论当成对另一台 A5 机器也成立——按开机必查表逐台核实。

## 已知陷阱

- **A5 profile 声明的 32 cube / 64 vec 与 Ascend950PR 物理的 28 cube / 56 vec 不一致**
  （AGENTS.md §5）；`block_dim` 超物理核数会在硬件 barrier 上死锁，先查这台机器的
  opp 算子包普查表再定 `block_dim`。
- 共享机器：先看 `npu-smi info` 的 Health 列，别 kill 或改别人的进程。
- 跨步视图的 D2H 在缺 `ascend950` 算子包的机器上要先整块 D2H 再切片（AGENTS.md §5 那条
  "先整块 D2H 再切" 的陷阱，C=1 时最容易只测到"恰好也过"的假阳性）。
- 这台机器上测的数字不能替另一台 A5 机器代言——每台单独测。
