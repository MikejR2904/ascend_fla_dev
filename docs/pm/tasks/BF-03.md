## 2026-09-19 追加（用户 D-PM-37）：格式转换也在 kernel 内，FP32 路径同样

- 分组（q/k 头共享）只能靠 kernel 内 head 索引，不得在 host 复制 / 重排 q/k；ATK 的 per-`H` 状态同理。FP32 路径（PK-03 现状）同样去掉 host 转换，输出改前改后逐位相同，两条路径都过 host 算子审计。

## 2026-09-20 Cube 澄清（PM 裁定，依排队申领人在 #102 的只读预检；PM 核实成立）

原规格这句话是我照着 BF-04（它的输出阶段确有 cube 数据通路）类推写的，但 BF-03 的两个只读起点——PK-03 的 `pgdn_chunk_fwd` 与已合入的 BF-01——**都是纯 Vector 递推 / 分块实现，没有 L0A / L0B / L0C / MMAD 的 Cube 数据通路**
（`kernels/stages.py` 五阶段只用 UB / VF；`atk_tile` 在 FP32 VF 里归一化并算 ATK）。所以：

- **Cube 不是硬要求**。接受与已合入 BF-01 一致的 **Vector 精度方案**：真实 BF16 `q/k/v` 直接进自编译 kernel，kernel 内 FP32 归一化与 ATK，保留 FP32 的 `q_norm` / `k_read` / `k_write` 与递推中间边，
  末端直接写 BF16 `o`；主状态与 ATK 状态保持 FP32；**不声称 BF16 Cube 吞吐提升**（BF-01 评审时 BF16 与 FP32 墙钟持平，这里同样只记实测，不设速度门槛）。
- 硬要求仍是：dtype 转换与格式转换都在自编译 kernel 里（D-PM-35 / D-PM-37）；FP32 公共路径改前改后逐位相同；host 两条 dtype 路径都只有分配 / 元数据 / 校验 / launch（真机审计）；预算 `min(1e-2, 3F)`、先校准、事后不得放宽；
  `k_read` / `k_write` 不对称与 per-H 的 ATK 状态保持。
- 想在 Vector 之外另做 Cube 路径是另一件事（要单独立项、另做数据流 / 精度预检），不夹带在本任务里；也不能把「只改了输入输出类型的 Vector 实现」说成实现了 Cube。

## 这条任务是怎么来的

用户 2026-09-19（D-PM-35）：BF16 计算必须在 kernel 里做，不能在 host 侧完成；后续 BF16 优先。PGDN 前向（PK-03）现在的 BF16 入口是 `q.float()` → FP32 kernel → 输出转回（`ascend_fla/ops/pgdn_chunk_fwd.py`），host 侧加宽。

## 范围

- 域与 PK-03 逐项一致（GDN 分组域 + ATK：`g_atk` / `beta_atk` / `log_atk_scale` per-`H`，`initial_state` / `initial_A_state` 只接 None，归一化必须开启，`block_dim∈{1,2}`）。
  BF16 的 `q/k/v` → BF16 的 `o`；`final_state`、`final_A_state` 仍 FP32。
- **q/k 的 `F.normalize`（`eps=1e-12` 语义，PK-03 已接受）必须在 kernel 里做**：BF16 q/k 进 kernel，kernel 内 FP32 归一化；host 不得预归一化。（原文这里还写了「再作 cube 的 BF16 operand」——2026-09-20 澄清：**Cube 不是硬要求**，见下面的「Cube 澄清」。）
  ATK 递推、有界 squash、读 / 写 key 不对称（`k_read` / `k_write`）保持 PK-03 的语义，在 kernel 里。
- 起点（只读）：PK-03 的 FP32 单元与 `BF-01` 的 BF16 GDN 单元。新建 `kernels/projects/a5/pgdn_chunk_fwd_bf16/`。

## 已知陷阱

- PGDN 的 naive **做** `F.normalize`，PKDA 的不做（`docs/research/pkda_semantics.md` §7）；别把两个算子的结论互相套用。
- 近零行的归一化在 BF16 下分叉最容易被漏掉：网格必须含近零行，并量化写明与 FP32 路径的差。
